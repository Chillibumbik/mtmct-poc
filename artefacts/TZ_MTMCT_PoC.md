## 1. Назначение и постановка задачи

**Исходная формулировка.** Разработать алгоритм, который отслеживает движение людей на видеозаписях нескольких камер и объединяет наблюдения одного человека в единый сквозной трек (Multi-Target Multi-Camera Tracking, MTMCT).

**Цель PoC.** Получить работающее локальное приложение, которое:

1. принимает синхронизированные видео N камер (из открытого датасета или загруженные пользователем);
2. строит сквозные треки людей с глобальными ID (`global_tracks.csv`);
3. измеряет качество всеми релевантными метриками (внутри камер, между камерами, по идентичностям, по ресурсам) и показывает их в полноценном веб-интерфейсе;
4. позволяет из UI запускать прогоны, проверять гипотезы (замена модулей, веса стоимостей, пороги), сравнивать прогоны и смотреть видео с наложенными глобальными ID.

**Кому.** Команде хакатона/исследователю, который выбирает подход MTMCT под свои данные и хочет видеть, какой блок даёт какой вклад.

**Критерий успеха (кратко).** Пайплайн проходит end-to-end на ≥ 4 открытых датасетах двух типов (с перекрытием и без), все метрики считаются автоматически и видны в UI, абляции показывают вклад каждого блока, всё укладывается в ресурсы ноутбука (§4). Подробно — §15.

## 2. Глоссарий

| Термин | Значение |
|---|---|
| Детекция | рамка человека на кадре одной камеры (`x, y, w, h, score`) |
| Треклет | последовательность детекций одного человека внутри одной камеры, полученная трекером (локальный ID) |
| Портрет треклета | агрегированное описание внешнего вида треклета: средний L2-нормированный эмбеддинг по top-K качественным рамкам + галерея K эмбеддингов |
| Точка ног | точка опоры человека на изображении (низ-центр рамки или середина лодыжек по позе) |
| Мировые координаты / BEV | координаты на плоскости пола (м), полученные гомографией изображение → пол |
| Глобальный ID | идентификатор человека, общий для всех камер |
| Сквозной трек | все наблюдения (рамки) одного глобального ID во всех камерах |
| Профиль `overlap` | камеры видят общую зону, есть калибровка → главная стоимость — геометрия |
| Профиль `nonoverlap` | камеры не перекрываются → главные — внешний вид и времена переходов |
| Oracle-режим | треклеты берутся из GT-разметки (заглушка «до треклетов»), проверяется только межкамерная ассоциация |
| False merge | два разных человека получили один глобальный ID |
| False split | один человек получил несколько глобальных ID |
| Handover | переход человека из одной камеры в другую |

## 3. Границы

### 3.1 Входит

- Офлайн (батч) пайплайн каскадного типа (подход «A»: детектор → трекер в камере → re-ID → чистка треклетов → портрет ∥ геометрия → межкамерная ассоциация → постобработка → оценка).
- Два профиля ассоциации на общем ядре: `overlap` и `nonoverlap`; переключение — только конфигом.
- Oracle-режим (GT-треклеты) для изоляции ошибок ассоциации.
- Реестр взаимозаменяемых компонентов и проверка гипотез (абляции, перебор по сетке).
- Веб-приложение FastAPI + React: данные, запуск прогонов и sweep-ов, живой прогресс, эксперименты и сравнение, разбор ошибок, синхронный плеер камер, BEV, ресурсы.
- Загрузка собственного набора видео нескольких камер (GT и калибровка — опционально).
- Документация: README, архитектура, отчёт по экспериментам (`artefacts/REPORT.md`).

### 3.2 Опционально (после основного объёма)

- Онлайн-вариант решателя (банк признаков + Hungarian, без использования будущих кадров) для сравнения офлайн/онлайн.
- Поза (RTMPose) для точки ног.
- Вспомогательный признак лица (YuNet + SFace) за флагом, **по умолчанию выключен** (биометрия, §13).

### 3.3 Не входит

- Обучение/дообучение нейросетей (используются только предобученные веса; разрешена калибровка порогов на tune-сплитах).
- Подходы с ранним слиянием в BEV (EarlyBird, MVDet, TrackTacular) и сквозные модели (MCTR, MOTIP) — требуют GPU-обучения.
- Работа в реальном времени с RTSP, продакшен-развёртывание, авторизация пользователей.
- Идентификация конкретных людей (сопоставление с базой известных лиц).

## 4. Ограничения и ресурсы

| Ресурс | Значение | Следствие |
|---|---|---|
| CPU | Intel i5-12450H, 8 ядер / 12 потоков, AVX2, без AVX-512 | инференс только CPU; OpenVINO основной рантайм, ONNX Runtime запасной |
| GPU | Intel UHD (iGPU), NVIDIA нет | iGPU через OpenVINO — только как гипотеза ускорения детектора |
| RAM | 16 ГБ, бюджет ≤ 60–70 % | **жёсткий лимит пикового RSS всего приложения ≤ 10 ГБ**, целевой ≤ 6 ГБ |
| Диск | ~99 ГБ свободно | суммарно данные + кеш + модели ≤ 40 ГБ |
| Python | 3.12, менеджер `uv` | |
| Node | ≥ 22 LTS, `pnpm` | для фронтенда |
| Docker | есть | `docker compose` как альтернативный запуск |

Технические следствия:
- видео декодируются потоково, кадры в память целиком не загружаются;
- обработка с прореживанием до `target_fps` (по умолчанию 10) и ограничением длинной стороны входа детектора;
- модели — ONNX / OpenVINO IR; PyTorch допускается только в необязательной группе зависимостей `export` для однократного экспорта весов;
- одна тяжёлая задача (прогон) выполняется одновременно; ассоциация и оценка — лёгкие и могут идти параллельно с UI.

### 5.2 Сплиты и протокол

- Параметры (пороги, веса, окна переходов) подбираются **только на tune-сплите**, итоговые цифры — на test-сплите. В UI сплит виден у каждого прогона.
- `epfl_terrace`: весь как dev (без итоговых цифр).
- `campus`: tune = Garden1, test = Garden2.
- `wildtrack`: стандартный сплит — tune = первые 90 % размеченных кадров, test = последние 10 % (сопоставимо с литературой); дополнительно — весь набор.
- `chirla`: tune = seq_001 (+ ещё одна при наличии), test = другие 1–2 последовательности; окна переходов между камерами оцениваются по GT tune-сплита.
- `aic24`: tune = первая половина времени, test = вторая половина.

### 5.3 Канонический формат после `ingest`

Каждый датасет приводится адаптером к единому виду `data/<dataset>/<sequence>/`:

```
cameras.json      # список камер
gt.parquet        # опционально: GT
topology.json     # опционально: окна переходов (nonoverlap), генерируется на tune
meta.json         # источник, лицензия, тип перекрытия, рекомендуемый профиль, сплиты
videos/<camera_id>.<ext> | frames/<camera_id>/%06d.jpg
```

`cameras.json`:

```json
{"cameras": [{
  "camera_id": "c0",
  "source": "videos/c0.avi",
  "fps": 25.0, "width": 360, "height": 288,
  "frame_offset": 0,
  "homography_img2world": [[...],[...],[...]] | null,
  "world_units": "m"
}]}
```

`gt.parquet`: `camera_id:str, frame_id:int32, person_id:int64, x,y,w,h:float32, world_x, world_y:float32|null`.

Синхронизация: `frame_offset` приводит кадры всех камер к общей шкале; общее время `ts = (frame_id + frame_offset) / fps` (сек).

## 6. Архитектура

### 6.1 Общая схема

```
        ┌───────────── Разработчик «A» (нейросети) ─────────────┐                 ┌──────── «B» (алгоритмы) ────────┐
video → │ ingest → detect → track → reid → refine → (foot point) │ → cache/v1/ → │ portrait ∥ geometry → associate │ → global_tracks.csv → eval → metrics
        └────────────────────────────────────────────────────────┘      ▲        │ → postprocess                   │
                                                 oracle: GT-треклеты ───┘        └─────────────────────────────────┘
                     FastAPI (REST + SSE) ── worker (очередь задач в SQLite) ── React SPA
```

Стык «треклеты» — контракт данных (§7). Всё, что до стыка, — тяжёлое (CPU-инференс), кешируется; всё, что после, — лёгкое и перезапускается за секунды, поэтому гипотезы ассоциации перебираются дёшево.

### 6.2 Структура репозитория


### 6.3 Реестр и конфиги

- Каждый взаимозаменяемый компонент регистрируется: `@register("detector", "yolox_s")`. Категории: `detector`, `tracker`, `reid`, `foot_point`, `cost`, `solver`, `postprocess`.
- У компонента — pydantic-схема параметров; API отдаёт реестр с JSON-схемами, UI строит формы автоматически.
- Конфиг прогона = `base.yaml` ⊕ профиль ⊕ датасет ⊕ переопределения из UI (точечные ключи). Итоговый конфиг сохраняется в прогон целиком.
- Новый вариант добавляется рядом, а не вместо: базовый остаётся рабочим.

Пример фрагмента конфига ассоциации:

```yaml
associate:
  costs:
    appearance: {weight: 1.0, agg: mean}        # mean | gallery_median | gallery_min
    geometry:   {weight: 0.5, gate_m: 1.5}      # только overlap
    time:       {weight: 0.0}                   # nonoverlap: окна из topology.json
  constraints: {same_camera_overlap: cannot_link, max_speed_mps: 3.0}
  solver: {name: agglomerative, linkage: average, threshold: 0.45}
```

### 6.4 Кеширование и идемпотентность

- Путь кеша: `cache/v1/<dataset>/<sequence>/<stage>-<hash8>/`, где `hash8` — хеш (конфиг стадии + хеши входных стадий + версия весов). `v1` — версия контракта; несовместимое изменение схемы → `v2`.
- В каждой папке `manifest.json`: стадия, конфиг, входы, версии пакетов и весов (sha256), время, длительность, статус.
- Стадия с готовым кешем не пересчитывается. Прерванная стадия не оставляет «полуготовый» кеш (запись во временную папку + атомарное переименование).

## 7. Контракты данных (`src/mtmct/io`)

Все таблицы — Parquet (pyarrow), валидируются pandera-схемами на запись и чтение.

| Файл | Колонки | Примечания |
|---|---|---|
| `detections.parquet` | `camera_id:str, frame_id:int32, ts:float64, x,y,w,h:float32, score:float32` | координаты в пикселях исходного разрешения; только класс person |
| `tracklets.parquet` | `camera_id, frame_id, ts, tracklet_id:int64, x,y,w,h, score, quality:float32, foot_x, foot_y:float32, world_x, world_y:float32?, emb_idx:int32 (-1 нет)` | `tracklet_id` уникален в пределах последовательности (кодирование камеры в старших разрядах) |
| `embeddings.npy` + `embeddings_index.parquet` | `float16 [N, D]`, L2-нормированы; индекс: `emb_idx, camera_id, frame_id, tracklet_id` | |
| `portraits.parquet` | `tracklet_id, camera_id, t_start, t_end, n_boxes, mean_quality, emb_mean_idx, gallery_idx:list[int32], entry_xy, exit_xy:list[float]?` | средний эмбеддинг — в `portraits.npy` |
| `global_tracks.csv` | `camera_id, global_id, frame_id, x, y, w, h[, world_x, world_y]` | итоговый результат, формат со схемы проекта |
| `metrics.json` | см. §9 | |
| `runtime.json` | время, FPS, латентности p50/p95, пиковая RAM по стадиям | |

Oracle-режим пишет `tracklets.parquet` из `gt.parquet` (локальный ID = GT ID в пределах камеры, без межкамерной информации) — тот же контракт, поэтому ассоциация не знает, откуда треклеты.

## 8. Стадии пайплайна

Для каждой стадии: базовый вариант (default) и гипотезы для сравнения. Все параметры — в конфиге.

### 8.1 `ingest` / `video`
- Адаптеры: `epfl_terrace`, `campus`, `wildtrack`, `chirla`, `aic24`, `custom`.
- `fetch`: загрузка по официальным ссылкам с докачкой, проверкой размера/sha, прогрессом в UI. CHIRLA — через `huggingface_hub` с токеном пользователя (токен в UI не вводится и не сохраняется приложением; используется локальная авторизация `hf auth login`).
- Потоковое чтение (OpenCV/PyAV), прореживание до `target_fps`, общая шкала времени.
- Прокси-видео для UI: H.264, длинная сторона ≤ 960, ffmpeg; создаётся один раз на последовательность.

### 8.2 `detect`
- **Базовый:** YOLOX-s (Apache-2.0, официальный ONNX), OpenVINO CPU, вход 640, класс person, `conf ≥ 0.3`, NMS 0.45, батч по кадрам.
- Гипотезы: YOLOX-tiny 416 (скорость); D-FINE-N / DEIM-N (Apache-2.0); YOLO11n/YOLO26n — только в изолированном адаптере (AGPL-3.0, необязательная зависимость); OpenVINO iGPU; INT8 (NNCF).

### 8.3 `track` (внутри камеры)
- **Базовый:** ByteTrack из Roboflow `trackers` (Apache-2.0) без ReID внутри трекера.
- Гипотезы: BoT-SORT (CMC), OC-SORT. BoxMOT (AGPL) — не используется в базовой сборке.
- Обоснование: ReID внутри трекера — 70–80 % времени кадра; признаки считаются один раз после трекинга (§8.4).

### 8.4 `reid`
- **Базовый:** OSNet-AIN x1_0 (веса torchreid, MSMT17; код MIT), экспорт в ONNX → OpenVINO, вход 256×128, D = 512.
- Сэмплинг рамок: каждая `stride`-я рамка треклета (по умолчанию 3) + принудительно top-K по качеству; рамки с сильным перекрытием (IoU с соседом > 0.3) и обрезанные краем кадра не эмбеддятся, если есть альтернативы.
- Гипотезы: OSNet x0_25 (скорость); Intel OMZ `person-reidentification-retail-0287` (без PyTorch); CLIP-ReID — офлайн-«потолок» качества, если укладывается в ресурсы.
- Санити: CMC/mAP на треклетах (§9.4) — проверка признаков независимо от трекинга.

### 8.5 `refine` (чистка треклетов — главный источник ошибок MTMCT)
- Разрез треклета при скачке внешнего вида: косинусное сходство средних эмбеддингов соседних окон < `split_thr`.
- Склейка обрывов внутри камеры: конец A → начало B при разрыве ≤ `max_gap` с, близком положении и сходстве внешнего вида.
- Фильтр: длина < `min_len` кадров или средний score < `min_score` → удаление.
- Интерполяция пропусков внутри треклета ≤ `interp_gap` кадров.
- Качество рамки `quality ∈ [0,1]` = комбинация относительной площади, score детектора, отсутствия перекрытия и обрезки краем.

### 8.6 `portrait` ∥ `geometry`
- Портрет: top-K (по умолчанию 10) рамок по `quality` → среднее L2-нормированное + галерея K.
- Точка ног: низ-центр рамки (базовый); гипотеза — лодыжки RTMPose-t (`rtmlib`).
- Гомография изображение → пол из калибровки датасета (`H = K [r1 r2 t]` для плоскости z = 0, либо готовая матрица); сглаживание мировой траектории скользящим средним; точки вне области интереса помечаются.
- Для `nonoverlap` без калибровки — только времена входа/выхода и позиции на изображении (зоны входа/выхода).

### 8.7 `associate` (межкамерная ассоциация — здесь различаются подходы)
Объект ассоциации — треклеты. Матрица расстояний `D = Σ wₖ·dₖ / Σ wₖ`, запреты → ∞.

| Стоимость | Определение | Профиль |
|---|---|---|
| `appearance` | `1 − cos(portraitᵢ, portraitⱼ)`; варианты агрегации: среднее / медиана по галереям / минимум | оба |
| `geometry` | при пересечении по времени: средняя дистанция на полу по общим моментам / `gate_m`, обрезка в [0,1]; > `gate_m` → cannot-link; без пересечения — проверка правдоподобия скорости перехода ≤ `max_speed_mps` | overlap |
| `time` | время перехода Δt между выходом из камеры i и входом в j; вне окна `[lo, hi]` пары камер (квантили 5–95 % по GT tune-сплита + запас) → cannot-link или штраф; ненаблюдавшиеся пары — штраф | nonoverlap |

Жёсткие ограничения: два треклета одной камеры, пересекающиеся по времени, — cannot-link; в одном кластере не более одного треклета на камеру в каждый момент времени.

Решатели:
- **Базовый:** агломеративная кластеризация (average linkage) с учётом cannot-link (собственная реализация на очереди с приоритетами: слияние запрещено, если нарушает ограничение), порог `threshold`.
- Гипотезы: k-reciprocal re-ranking матрицы `appearance` перед кластеризацией; anchor-guided (AIC23: иерархическая кластеризация → якоря → Hungarian по якорям); Hungarian для пары камер; онлайн-решатель (опц., §3.2).

### 8.8 `postprocess`
- Удаление глобальных треков короче `min_global_len` кадров, видимых только в одной камере (настраивается).
- Устранение дублей «один глобальный ID — две рамки в одном кадре одной камеры» (оставить рамку с большим score).
- Запись `global_tracks.csv` и MOT-файлов по камерам.

## 9. Оценка и метрики (`src/mtmct/eval`)

Все метрики считаются автоматически в конце прогона и сохраняются в `metrics.json` и в БД. GT прореживается до тех же кадров, что обработаны пайплайном.

### 9.1 Внутри камер (per-camera, затем среднее и сумма)
HOTA, DetA, AssA, LocA, IDF1, IDP, IDR, MOTA, MOTP, IDSW, FP, FN, Frag — через TrackEval (MotChallenge2DBox), IoU-порог по умолчанию для CLEAR/Identity 0.5.

### 9.2 Между камерами (главные метрики)
- **Склейка камер:** камеры конкатенируются по оси времени со сдвигом `frame' = cam_index · (max_frame + 1) + frame`, GT ID = глобальный ID человека, предсказанный ID = `global_id`. На этой последовательности: **HOTA, AssA, IDF1, IDP, IDR** (MOTA — справочно).
- Для датасетов с мировыми координатами — опционально метрики на плоскости пола (порог 0.5–1 м), как в MMPTrack/AIC.
- TrackEval вендорится (закреплённый коммит, патч совместимости с numpy 2); IDF1 сверяется с `py-motmetrics` в тестах.

### 9.3 Идентичности (кластерные)
Каждый предсказанный треклет сопоставляется GT-человеку (большинство рамок с IoU ≥ 0.5), далее глобальные ID трактуются как кластеризация:
- pairwise Precision / Recall / F1; BCubed P / R / F; purity / inverse purity;
- число предсказанных глобальных ID против числа GT-людей;
- **false merges** (кластер содержит > 1 GT-человека) и **false splits** (GT-человек в > 1 кластере) — количество и список с примерами для UI;
- **handover success rate** — доля переходов GT-человека между камерами, при которых глобальный ID сохранился;
- кривая P/R и IDF1 по порогу решателя (дешёвый перебор только ассоциации).

### 9.4 ReID-санити
CMC rank-1 / rank-5 и mAP: запрос — портрет треклета в камере i, галерея — треклеты других камер.

### 9.5 Абляции (обязательный набор)
| Абляция | Сравнение |
|---|---|
| Источник треклетов | oracle (GT) vs реальный пайплайн → вклад детектора/трекера vs ассоциации |
| Стоимости | appearance only → + geometry (overlap) / + time (nonoverlap) → полная |
| Чистка треклетов | без `refine` vs с `refine` |
| Портрет | среднее всех рамок vs top-K по качеству |
| Решатель | агломеративная vs + re-ranking vs anchor-guided |
| ReID-модель | OSNet-AIN x1_0 vs x0_25 vs OMZ-0287 |
| Детектор | YOLOX-s vs YOLOX-tiny (+ D-FINE-N) |

### 9.6 Ресурсы
Время каждой стадии, FPS (обработанные кадры / с) на камеру и суммарно, латентность p50/p95 на кадр (детектор) и на рамку (ReID), пиковый RSS процесса воркера (сэмплинг psutil каждые 0.5 с), средняя загрузка CPU, размер кеша.

## 10. Приложение

### 10.1 Бэкенд (FastAPI)

- Процессы: `api` (uvicorn) и `worker` (отдельный процесс). Состояние — SQLite (`db/mtmct.sqlite`, SQLModel), артефакты — в файловой системе.
- Таблицы: `datasets`, `runs`, `jobs`, `job_events`, `metrics` (run_id, scope, name, value — для быстрых таблиц и сравнения).
- Задачи (`jobs`): `dataset_fetch`, `dataset_prepare` (ingest + прокси-видео), `run`, `sweep` (порождает дочерние `run`), `eval_only`. Статусы `queued → running → done | failed | cancelled`.
- Воркер берёт задачи по одной (CPU), публикует события прогресса (стадия, %, ETA, сообщения лога) в `job_events`; API отдаёт их по SSE. Отмена — флаг, проверяемый между батчами; кеш при отмене не портится (§6.4).
- После перезапуска воркер помечает «зависшие» `running` как `failed` с причиной; задачу можно перезапустить, готовые стадии подхватятся из кеша.

Эндпоинты (префикс `/api`):

| Метод | Путь | Назначение |
|---|---|---|

OpenAPI-схема генерируется автоматически; TypeScript-типы фронтенда генерируются из неё (`openapi-typescript`).

### 10.2 Фронтенд (React SPA)

Стек: React 19 + Vite + TypeScript (strict), Tailwind CSS v4 + shadcn/ui, TanStack Query (данные), TanStack Router (маршруты), ECharts (графики), zod (формы), Vitest + Playwright. Язык интерфейса — русский, названия метрик — общепринятые английские с подсказками (что значит метрика, чем больше — тем лучше). Светлая и тёмная темы.

| Экран | Содержимое |
|---|---|
| **Обзор** | лучший прогон на каждом датасете (test-сплит): плитки HOTA / IDF1 межкамерные, handover, FPS, RAM; статус системы и очереди |
| **Данные** | карточки датасетов (тип перекрытия, камеры, размер, лицензия, статус) с кнопкой «Скачать/Подготовить» и прогрессом; превью кадров камер; загрузка собственного набора |
| **Новый прогон** | выбор датасета/последовательности/сплита, режима (full/oracle), профиля; по стадиям — выбор компонента из реестра и формы параметров (из JSON-схем); веса стоимостей и порог; оценка времени; кнопка «Запустить». Вкладка «Sweep» — сетка значений, число прогонов, оценка времени |
| **Задачи** | очередь, живой прогресс по стадиям (SSE), ETA, логи, отмена, перезапуск |
| **Эксперименты** | таблица прогонов: все ключевые метрики, датасет, сплит, режим, конфиг-диф от базового; сортировка/фильтры; выбор 2–N прогонов → сравнение (дельты, подсветка лучшего); графики абляций (столбцы по вкладу блоков), кривая P/R и IDF1 по порогу |
| **Разбор прогона** | метрики по камерам и межкамерные (с пояснениями), кластерные метрики, матрица переходов камера → камера (успешные / проваленные handover), список false merge / false split с миниатюрами треклетов и переходом в плеер к нужному моменту; ReID-санити |
| **Плеер** | синхронная сетка камер (общая шкала времени, скорость, покадровый шаг), рамки и глобальные ID на canvas (`requestVideoFrameCallback`), цвет по глобальному ID; режимы наложения: предсказание / GT / расхождения; клик по человеку → его маршрут (таймлайн по камерам, миниатюры); BEV-карта траекторий для датасетов с калибровкой |
| **Ресурсы** | время и доля стадий, FPS, p50/p95, пиковая RAM по прогонам; сравнение компонентов по скорости |

Требования к UX: состояния загрузки/пусто/ошибка на каждом экране; длинные операции — только через задачи с прогрессом; деструктивные действия — с подтверждением; ссылки на прогоны и людей — постоянные URL.

### 10.3 Запуск

- `make setup` — `uv sync`, `pnpm install`, загрузка весов моделей с проверкой sha256.
- `make dev` — api + worker + vite dev server одной командой; UI на `http://localhost:5173` (API на `:8000`).
- `make up` — `docker compose up` (образ api/worker + nginx со сборкой фронтенда) → `http://localhost:8080`.

- Внутренний CLI (`uv run mtmct …`) повторяет основные действия для тестов и агентов, пользователю не требуется.

## 12. Качество и тестирование

- **TDD** для `eval`, `associate`, `refine`, `io`: тесты пишутся до кода.
- **Eval:** синтетический мини-GT с заранее известными ошибками (ID switch, false merge, false split, пропуск) → ожидаемые значения метрик; сверка IDF1 TrackEval vs py-motmetrics; идеальное предсказание = 1.0.
- **Associate:** синтетические треклеты с известной кластеризацией; соблюдение cannot-link; инвариантность к перестановке входа.
- **Контракты:** pandera-схемы, круговые тесты записи/чтения.
- **Интеграция:** smoke-e2e на `epfl_terrace` (обрезка до 30 с, все стадии, ≤ 2 мин) — в `make check`; полный прогон — отдельная цель `make e2e`.
- **API:** pytest + httpx (TestClient), фиктивный воркер.
- **Фронтенд:** Vitest для логики (синхронизация плеера, форматирование метрик), Playwright — сценарий «выбрать датасет → запустить oracle-прогон → увидеть метрики → открыть плеер».
- **Статический анализ:** ruff (lint + format), mypy (strict для `io`, `associate`, `eval`), tsc strict, eslint; pre-commit.
- **Ревью:** каждая задача проходит ревью (переусложнение, выход за зону файлов, удаление нужного) до слияния в `main`; `main` всегда зелёный.

## 13. Лицензии, данные, этика

- Используются только официально распространяемые датасеты с указанием лицензий в UI; сырые данные не распространяются.
- Модели базовой сборки — с пермиссивными лицензиями (YOLOX Apache-2.0, OSNet MIT-код, `trackers` Apache-2.0, OpenVINO Apache-2.0). AGPL-компоненты (ultralytics, boxmot) — только как необязательные адаптеры, отмеченные в UI. Веса ReID обучены на исследовательских датасетах — PoC только для исследовательского использования.
- Признак лица — биометрия (152-ФЗ, GDPR ст. 9): в базовой сборке не используется; если включается (опция), то только на датасетах с согласием участников (CHIRLA), без сопоставления с базами известных людей.
- В демо-материалах (скриншоты, отчёт) лица на реальных датасетах — по возможности размыты.

## 14. План гипотез

| ID | Гипотеза | Как проверяется | Ожидание |
|---|---|---|---|
| H1 | Oracle-треклеты дают высокий межкамерный IDF1; разрыв oracle → full показывает долю ошибок до стыка | §9.5, все датасеты | разрыв значимый; ошибки трекинга внутри камеры — главный источник |
| H2 | Геометрия (гомография + точка ног) сильнее внешнего вида при перекрытии | appearance vs + geometry на campus/wildtrack/aic24 | + geometry ↑ IDF1 |
| H3 | Временные окна переходов критичны без перекрытия | appearance vs + time на chirla | + time ↑ IDF1, ↓ false merges |
| H4 | Top-K портрет по качеству лучше среднего всех рамок | §9.5 | ↑ rank-1 и IDF1 |
| H5 | `refine` снижает false merges | с/без | ↓ false merges |
| H6 | k-reciprocal re-ranking улучшает кластеризацию | с/без | ↑ pairwise F1 |
| H7 | Anchor-guided решатель (AIC23) лучше агломеративной | сравнение решателей | неочевидно |
| H8 | Лёгкие модели (YOLOX-tiny, OSNet x0_25) — приемлемая потеря качества при кратном ускорении | качество vs время | компромисс на графике |
| H9 | Поза (лодыжки) точнее низа рамки для точки ног | опц. | ↑ при окклюзиях |
| H10 | Онлайн-решатель уступает офлайну на 5–10 HOTA | опц. | подтверждение литературы |

Итог гипотез фиксируется в `artefacts/REPORT.md` с таблицами и ссылками на прогоны.

## 16. Риски

| Риск | Вероятность | Митигация |
|---|---|---|

## 17. Процесс разработки

- Оркестрация агентами по схеме agent-fleet: мастер (Opus) держит контекст и решения в `agent-dump/HANDOFF.md`, очередь — `agent-dump/TASKS.md`; исполнители — субагенты Claude (Opus для сложных задач, Sonnet — для типовых); ревьюер (Opus) после каждой задачи. Codex не используется.
- Зоны файлов (не пересекаются при параллельной работе): **A** — `detect/ track/ reid/ refine/ video/`; **B** — `associate/ geometry/ portrait/ postprocess/ eval/`; **C** — `api/ worker/ pipeline/ runtime/`; **D** — `web/`; **данные** — `data/` адаптеры. Общие `io/`, `registry.py`, `config.py`, `configs/base.yaml` меняет только мастер отдельной правкой.
- Заглушка с первого дня: oracle-треклеты (GT) в формате контракта, чтобы ветка B работала до готовности A.
- Короткие ветки, маленькие изменения, `main` всегда рабочий; незаконченное — за флагом в конфиге (выключено).
- Каждое изменение: тесты → ревью → слияние. Эксперименты — в `outputs/<run_id>/`, журнал прогонов — в БД и `REPORT.md`.
