# MTMCT PoC — сквозное отслеживание людей по видео нескольких камер

Локальное приложение (CPU-only): берёт синхронизированные видео N камер, строит сквозные треки людей с
глобальными ID, считает метрики качества (внутри камер, между камерами, по идентичностям, по ресурсам) и показывает
всё в веб-интерфейсе. Из UI можно скачать открытый датасет, запустить прогон (`full` — от видео, `oracle` — от
GT-треклетов), перебрать параметры сеткой (sweep), сравнить прогоны и посмотреть видео с наложенными глобальными ID.

- Постановка, метрики, критерии приёмки: [`artefacts/TZ_MTMCT_PoC.md`](artefacts/TZ_MTMCT_PoC.md)
- Результаты экспериментов и выводы по гипотезам: [`artefacts/REPORT.md`](artefacts/REPORT.md)

## Архитектура

```
 видео N камер ──► detect ──► track ──► reid ──► refine ──┐        (тяжёлые стадии, кеш на диске)
 (или GT-треклеты в oracle)                                │
                                          portrait ∥ geometry ──► associate ──► postprocess ──► eval
                                                           (дёшево, пересчитывается всегда)

 браузер ── React SPA ── HTTP/SSE ──► FastAPI (api) ──► SQLite (db/) ◄── worker ── run_pipeline
                                          │                                  │
                                          └──────────── файлы: data/ cache/ models/ outputs/
```

- Каскад «A»: детектор (YOLOX) → трекер в камере (ByteTrack/BoT-SORT/OC-SORT) → ReID (OSNet / OMZ-0287) → чистка
  треклетов → портрет ∥ геометрия (гомография + точка ног) → межкамерная ассоциация → постобработка → оценка.
- Тяжёлые стадии кешируются в `cache/v1/<датасет>/<последовательность>/<стадия>-<hash8>/` (содержимое определяется
  хешем конфига), ассоциация и оценка пересчитываются за секунды — поэтому перебор порогов и весов быстрый.
- Компоненты (детектор, трекер, ReID, стоимости, решатель) подключаются через реестр; профили `overlap`
  (камеры видят общую зону, главное — геометрия) и `nonoverlap` (главное — внешний вид и времена переходов)
  переключаются только конфигом.
- Процессы: `api` (uvicorn) и один `worker` (задачи берутся по одной, чтобы не перегружать CPU/RAM). Состояние —
  SQLite, артефакты прогонов — файлы в `outputs/<id>/`.

## Требования

- Linux/macOS, Python 3.12, [`uv`](https://docs.astral.sh/uv/), Node ≥ 22 и `pnpm` (системный Node 18 не годится).
- Ориентир по ресурсам: 8+ ядер, 16 ГБ RAM (пик одного прогона ≤ 10 ГБ, цель ≤ 6 ГБ), ~40 ГБ диска под данные,
  кеш и модели. GPU не нужен. Docker (опционально) — для `make up`.
- Интернет нужен только для `make setup` и загрузки датасетов; после этого приложение работает офлайн.

## Быстрый старт

```bash
make setup     # uv sync, pnpm install, веса моделей (с проверкой sha256), экспорт OSNet в ONNX
make dev       # api (:8000) + worker + vite (:5173) одной командой; Ctrl+C останавливает всё
```

Откройте <http://localhost:5173>. Если Node установлен не в системные пути, `Makefile` добавляет в `PATH`
`~/.local/opt/node/bin`.

`make setup` ставит PyTorch (CPU) в отдельной группе зависимостей `export`: он нужен только для однократного
экспорта весов OSNet в ONNX (`scripts/export_osnet.py`), в рантайме инференс идёт через OpenVINO (запасной
вариант — ONNX Runtime).

### Docker

```bash
make setup     # на хосте: веса моделей (экспорт OSNet требует torch, в образ он не входит)
make up        # docker compose up --build -d  →  http://localhost:8080 (порт слушает только 127.0.0.1)
make down
```

Сервисы `api` и `worker` собираются из одного образа (`Dockerfile`: Node 22 собирает фронтенд, затем
`python:3.12-slim` + `uv`; FastAPI отдаёт `web/dist`). Каталоги `data/ cache/ models/ outputs/ db/` монтируются с
хоста, поэтому датасеты и веса не копируются в образ и не теряются при пересборке.

## Как пользоваться

1. **Данные.** Страница «Данные» — карточки датасетов (тип перекрытия, камеры, размер, лицензия). Кнопка
   «Скачать» ставит задачу: загрузка → подготовка → прокси-видео. Прогресс виден на странице «Задачи».
   - CHIRLA лежит в закрытом репозитории Hugging Face: примите условия на
     <https://huggingface.co/datasets/bdager/CHIRLA> и выполните `uv run hf auth login`.
   - Свои видео: «Данные» → «Загрузить свои видео» (N видеофайлов, опционально калибровка JSON и GT).
2. **Прогон.** «Новый прогон»: датасет, последовательность, сплит (`tune` — подбор параметров, `test` — итог),
   режим (`full` / `oracle`), профиль, компоненты по стадиям, веса стоимостей и порог решателя. Для быстрой проверки
   задайте `max_seconds` (например, 20) и режим `oracle` — это секунды, а не минуты.
3. **Sweep.** На той же странице вкладка «Sweep»: ключ конфига (например `associate.solver.params.threshold`) и
   список значений; декартово произведение превращается в серию прогонов. Параметры подбирайте на `tune`, не на `test`.
4. **Результаты.** «Эксперименты» — таблица прогонов, выбор 2–N прогонов → сравнение с дельтами; «Прогон» — все
   метрики с пояснениями, матрица переходов камера → камера, кривая по порогу; «Ошибки» — false merge / false split с
   миниатюрами; «Плеер» — синхронная сетка камер с рамками и глобальными ID, режимы «предсказание / GT /
   расхождения», маршрут человека, вид сверху (BEV) для откалиброванных датасетов; «Ресурсы» — время стадий, FPS,
   пиковая RAM.

### Метрики

| Группа | Метрики | Где смотреть |
|---|---|---|
| Внутри камеры (TrackEval, IoU 0.5) | HOTA, DetA, AssA, MOTA, IDF1 по каждой камере и среднее | страница прогона, «По камерам» |
| Между камерами | HOTA, AssA, IDF1, IDP, IDR, MOTA на склеенных глобальных треках | плитки вверху страницы прогона; таблица «Эксперименты» |
| Идентичности | pairwise F1, B-Cubed F, purity, число false merge / false split, handover success | «Разбор ошибок», страница прогона |
| ReID-санити | rank-1, rank-5, mAP по портретам треклетов разных камер | страница прогона |
| Ресурсы | wall time, FPS, p50/p95 по стадиям, пиковая RSS, CPU | «Ресурсы», страница прогона |
| Порог | P / R / IDF1 как функция порога решателя | страница прогона, «Эксперименты» |

Файлы прогона лежат в `outputs/<id>/`: `global_tracks.csv`, `metrics.json`, `runtime.json`, `config.yaml`, `log.jsonl`
(архив с ними отдаёт `GET /api/runs/<id>/export`). Названия метрик в UI — общепринятые английские, с подсказками.

## Структура репозитория

```
configs/            base.yaml, profiles/ (overlap, nonoverlap), datasets/, sweeps/
src/mtmct/
  data/             адаптеры датасетов (epfl_terrace, campus, wildtrack, chirla, aic24, custom)
  detect/ track/ reid/ refine/ portrait/ geometry/ associate/ postprocess/   стадии пайплайна
  pipeline/         оркестратор run_pipeline, кеш стадий, события, отмена, RAM-guard
  eval/             метрики (TrackEval, motmetrics, кластерные, handover, ReID)
  runtime/          профилирование (RAM/CPU/время стадий)
  api/ worker/ db.py  FastAPI, фоновый воркер, SQLite (SQLModel)
  io/ registry.py config.py components.py   контракты таблиц (pandera), реестр, конфиг, интерфейсы
web/                React 19 + Vite + TypeScript, e2e/ (Playwright), openapi.json → типы
tests/              unit/, integration/, e2e/
third_party/TrackEval   вендорная копия TrackEval (патч под numpy 2)
artefacts/          ТЗ и отчёт (бизнес-артефакты)
data/ cache/ models/ outputs/ db/   данные, кеш, веса, прогоны, БД (в git не попадают)
```

CLI (`uv run mtmct --help`: `fetch`, `prepare`, `run`, `catalog`, `api`, `worker`) — внутренний, для отладки и
тестов; пользователю достаточно UI.

## Тесты и проверки

```bash
make check     # ruff, mypy, pytest (без data/slow; pytest-смоук e2e входит и сам пропускается без данных), tsc, vitest, eslint
make e2e       # смоук на реальных данных: pytest -m e2e, затем Playwright (нужны data/epfl_terrace и models/)
```

- `tests/e2e/test_smoke.py` — API (TestClient) + воркер, oracle-прогон `epfl_terrace/terrace1` на 20 с:
  метрики есть, cross IDF1 ≥ 0.9, пиковая RAM записана. Без данных или моделей тест пропускается.
- `web/e2e/smoke.spec.ts` — Playwright: «Данные → Новый прогон (oracle, 20 с) → Задачи → метрики → плеер с рамками».
  Сам поднимает api + worker на изолированном `MTMCT_HOME` (свои БД/кеш; `data/` и `models/` подключаются
  ссылками), Vite запускается через `webServer`. Если порт 8000 уже занят (например, `make dev`), используется
  работающий бэкенд. Браузер: `cd web && pnpm exec playwright install chromium-headless-shell`; если в системе есть
  `/usr/bin/google-chrome`, берётся он (в Chromium от Playwright нет H.264, поэтому проверка опирается на рамки,
  а не на воспроизведение видео).
- Тесты, требующие скачанных датасетов, помечены `data`, долгие — `slow`; по умолчанию они не запускаются.

## Ограничения

- Только офлайн-обработка, CPU; режим реального времени и RTSP не поддерживаются.
- Обучение и дообучение нейросетей не выполняется — используются предобученные веса; пороги калибруются на `tune`.
- Качество `full`-режима ограничено трекингом внутри камеры: разрыв между `oracle` и `full` — основной источник
  ошибок (подробности — в [`artefacts/REPORT.md`](artefacts/REPORT.md)).
- Калибровка CAMPUS шумная, поэтому геометрия там «мягкая»; у CHIRLA нет калибровки, часть камер фактически
  перекрывается, а камеры 6–7 без людей.
- Одна тяжёлая задача за раз; если пик RAM превышает `data.max_rss_gb`, прогон останавливается с пояснением.
- Исследовательский прототип: без авторизации, API слушает только `127.0.0.1`. Лица на реальных данных в демо-материалах
  по возможности размывайте.
